⚡ Zero-Copy Architecture (`sendfile`)

Top Question

In standard web applications, sending a file to the network requires 4 context switches and 4 copy operations (Disk -> Kernel Page Cache -> User Space Application Buffer -> Kernel Socket Buffer -> NIC DMA Buffer).

// Traditional Path (4 Copies, 4 Context Switches):
read(fileDesc, buf, len) -> Disk to PageCache, PageCache to User Buffer
write(sockDesc, buf, len) -> User Buffer to Socket Buffer, Socket to NIC
// Kafka Zero-Copy Path (`sendfile` system call):
sendfile(sockDesc, fileDesc, &offset, count);
Data moves straight: Disk -> PageCache -> NIC (via scatter-gather DMA descriptor). 0 copies into user memory!
Key Interview takeaway: Kafka avoids JVM Garbage Collection pauses entirely for cached reads because data is held in the OS Page Cache, not JVM Heap!

🛡️ High Watermark (HW) vs LEO & ISR

Consistency

How Kafka prevents message loss and dirty reads across distributed replicas.

Log End Offset (LEO):
The offset of the next record to be written. Each replica has its own LEO as it fetches writes from the partition leader.
High Watermark (HW):
The highest offset replicated across ALL in-sync replicas (ISR). Consumers can ONLY read up to the HW, guaranteeing uncommitted messages are never exposed.
Durability Golden Rule:
acks = all (-1) + min.insync.replicas = 2 + replication.factor = 3
Guarantees that at least 2 replicas confirm write before success is returned to producer.

👑 KRaft (Kafka Raft Metadata Mode)

In modern Kafka (version 3.x+ and 4.0), Apache ZooKeeper is removed in favor of KRaft.

Legacy ZooKeeper Limitations:
  • Separate cluster to manage, monitor, and scale.
  • Metadata changes required dual-hop synchronization (Broker -> ZooKeeper -> Controller).
  • Slow failover: If the active Controller failed, the new Controller had to load all cluster metadata from ZK (causing minutes of partition offline downtime).
  • Topic partition limit (~200,000 per cluster max).
KRaft Advantages (Confluent Standard):
  • Quorum-based Raft consensus running inside Kafka itself.
  • Metadata stored in an internal topic (@metadata).
  • Standby controllers replicate metadata in real time; failover is instantaneous (milliseconds).
  • Supports millions of partitions on a single cluster.

🛠️ Linux SRE Command Arsenal & Troubleshooting Cheat Sheet

Confluent interviewers test practical command fluency. When an issue occurs on a broker, which tool do you use first?

$ iostat -xz 1 Disk I/O Latency & Saturation

Key Columns to Inspect: %util: Percentage of time device had I/O requests. Near 100% means saturated disk. r_await / w_await: Average time (in milliseconds) for read/write requests to be served. If w_await > 15ms on SSD/NVMe, storage is a bottleneck.

$ vmstat 1 CPU Run Queue & Memory Thrashing

Key Columns to Inspect: r: Number of runnable processes waiting for CPU. If r > number of CPU cores, the system is CPU-bound. b: Processes blocked waiting for I/O (Uninterruptible Sleep / D state). si / so: Swap in / Swap out. If non-zero, memory thrashing is active.

$ ss -s & ss -tulpn Socket Backlog & Network Connections

Checks for TCP socket exhaustion, high TIME-WAIT connections, and Recv-Q / Send-Q backlog. A growing Recv-Q on port 9092 means the broker is not reading incoming requests fast enough.

$ strace -c -p <pid> System Call Profiling

Measures percentage of CPU time spent inside kernel system calls (futex, epoll_wait, writev). Great for pinpointing lock contention or slow syscalls.

☸️ Running Kafka on Kubernetes (Confluent For Kubernetes)

Why Kafka brokers use StatefulSets with custom Operators instead of simple Deployments.

1. Headless Service DNS

Brokers must have deterministic network names (e.g. kafka-0.kafka-headless.prod.svc.cluster.local). Client producers cache metadata by broker hostname.

2. Persistent Volume Claims

Each replica has its own dedicated volume template (data-kafka-0). If Pod 0 is rescheduled to another node, it reattaches the same EBS/NVMe volume without data resync.

3. Multi-AZ Anti-Affinity

podAntiAffinity and topologySpreadConstraints prevent broker replicas of the same cluster from landing on the same physical host or AWS availability zone.
